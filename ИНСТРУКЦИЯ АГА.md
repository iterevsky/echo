# ИНСТРУКЦИЯ АГА

Практическое руководство для автора проекта «ЭХО»: как провести этап реализации вместе с Kimi Code Desktop, что именно ему отправлять, какую модель выбирать, как контролировать каждое изменение и как продолжать писать роман между техническими задачами.

Документ написан для автора, а не для программиста. Технические термины объясняются при первом использовании. Имена файлов, задач и команд оставлены в оригинальном виде — их нужно копировать точно.

**Статус этого документа.** Это навигационное пособие, а не технический источник истины. Если эта инструкция когда-либо разойдётся с рабочими документами, правы всегда они: ROADMAP.md v2.2 (что и в каком порядке делать), TASKS.md v4.2 (диагнозы и детали задач), DECISIONS.md v4.2 (решения автора), IMPLEMENTATION-PLAYBOOK.md v1.2 (как работает Kimi Code и тексты промптов), IMPLEMENTATION-STATUS.md v1.2 (текущее состояние дел). Эта инструкция только объясняет, как ими пользоваться.

**Версии документов, на которые опирается инструкция:** ROADMAP.md v2.2, TASKS.md v4.2, DECISIONS.md v4.2, IMPLEMENTATION-PLAYBOOK.md v1.2, IMPLEMENTATION-STATUS.md v1.2, CHANGELOG.md (запись от 2026-11-05). Если версии в вашем пакете новее — сверяйтесь с ними.

### 1.3. Главное правило файлового охвата

Каждая задача вправе менять **только те файлы, которые перечислены в её промпте** (поле FILES/AREAS). Есть ровно два исключения:

1. **`IMPLEMENTATION-STATUS.md` разрешён в каждом коммите задачи** — это обязательные операционные метаданные, даже если файл лежит вне охвата задачи. Это исключение не разрешает никаких других посторонних правок.
2. **У W-5 есть одно дополнительное условное исключение (точка S1):** если в ходе замеров реально изменились инженерные параметры качества, W-5 может в том же коммите обновить соответствующие числа в ROADMAP.md и IMPLEMENTATION-PLAYBOOK.md — строго только эти параметры. Если параметры не менялись, S1 закрывается одной строкой подтверждения в отчёте.

Если вы видите в коммите файлы, которых нет ни в промпте задачи, ни в этих двух исключениях, — это повод остановиться и разобраться (см. раздел 5).

## 2. Общий порядок работы простыми словами

1. Подготовьте документы и убедитесь, что репозиторий уже есть в рабочей области Kimi Code Desktop. **Ничего клонировать не нужно** — репозиторий `echo` уже на месте.
2. Выполните предполётную проверку репозитория и создайте утверждённую ветку разработки `work/echo-step4-implementation` от закреплённого коммита (PLAYBOOK §7.2). Если ветка вдруг уже существует — не перезаписывайте её; PLAYBOOK §7.8 описывает безопасный порядок действий.
3. Положите финальный пакет документов (шесть файлов плюс эту инструкцию) в корень репозитория.
4. Закоммитьте пакет документов по PLAYBOOK §7.3.
5. **Первой всегда выполняется задача B-0** — она записывает фактический базовый уровень проверок. Ни одна задача с кодом не начинается, пока B-0 не закоммичена.
6. После B-0 работа идёт по двум трекам. Трек 1 (задачи T) имеет утверждённый внутренний порядок. Трек 2 (задачи W, «вода») может начаться сразу после B-0 и **чередоваться** с Треком 1, но его внутренний порядок W-1 → … → W-9 строгий. Одновременно над одними файлами две задачи не работают никогда.
7. Перед каждой задачей сверьтесь с IMPLEMENTATION-STATUS.md и историей Git.
8. Скопируйте **полный** промпт нужной задачи из PLAYBOOK §8 в Composer Kimi Code.
9. Дайте Kimi Code выполнить ровно одну задачу с её проверками. **Одна задача = один коммит.**
10. Прочитайте отчёт о завершении, посмотрите список изменённых файлов и сам коммит, сравните с охватом задачи.
11. Переходите к следующей задаче, только когда выполнены зависимости и проверки зелёные (PENDING-AUTHOR-пункты — см. ниже — не блокируют).
12. Пункты PENDING-AUTHOR — это проверки на ваших физических устройствах и ваши визуальные оценки. Они ждут вас и **не считаются** выполненными Kimi. Не путайте их с проверками, которые Kimi сделал сам.
13. После W-9 выполняется финальная регрессия (S4) и разбор оставшейся авторской очереди.
14. Публикуете сайт **только вы**, вручную. Kimi Code не публикует, не отправляет изменения на сервер и не трогает боевой сайт никогда.

Эта инструкция не разрешает пропускать контрольные точки и не разрешает начинать реализацию до B-0.

## 3. Что именно отправлять в Kimi Code

### 3.1. Главное правило

**Не собирайте промпт для задачи вручную из кусков разных документов.** Всё уже собрано за вас:

- Утверждённые документы лежат в корне репозитория — Kimi Code умеет читать их сам.
- Вы копируете **один цельный промпт задачи** из раздела §8 файла `IMPLEMENTATION-PLAYBOOK.md` и отправляете его в Composer.
- Не нужно вставлять в каждое сообщение целиком ROADMAP, TASKS, DECISIONS или CHANGELOG.
- Каждый промпт уже содержит: правила безопасности, 13 пронумерованных полей (цель, доказательства, файлы, ожидаемое изменение, подход, запреты, критерии приёмки, проверки, регрессии, предусловия, текст коммита, шаблон отчёта, обновление статуса) — всё необходимое для выполнения.
- Если сессия прервалась, вы копируете **полный промпт возобновления** из PLAYBOOK §10, а не пересказываете прогресс своими словами.

### 3.2. Таблица «что отправлять на каждом этапе»

| Этап | Что вы отправляете | Откуда берётся | Зачем |
|---|---|---|---|
| Начальная настройка | Указание выполнить подготовку и документальную фиксацию по §§7.1–7.3 | IMPLEMENTATION-PLAYBOOK.md | Подготовить рабочую область и закоммитить утверждённые документы |
| Базовый уровень | Полный промпт **B-0** | PLAYBOOK §8, промпт B-0 | Записать реальный уровень проверок до любых изменений кода |
| Каждая задача T | Один цельный промпт со всеми 13 полями | Соответствующий промпт T… в PLAYBOOK §8 | Выполнить ровно одно исправление или улучшение |
| Каждая задача W | Один цельный промпт со всеми 13 полями | Соответствующий промпт W-… в PLAYBOOK §8 | Выполнить этап «воды» в его утверждённой фазе (лаборатория или продакшн) |
| Возобновление сессии | Полный промпт автономного возобновления | PLAYBOOK §10 | Восстановить фактическое состояние и продолжить следующую готовую задачу |

**Никогда не отправляйте только фрагмент** — заголовок задачи или одно поле «решение». Отправляйте весь блок промпта целиком, от строки SAFETY PREAMBLE до конца поля 13.

### 3.3. Какой документ на какой вопрос отвечает

- **ROADMAP** — что можно запускать следующим, зависимости, контрольные точки, приоритеты, финальная проверка.
- **TASKS** — в чём диагноз и какие изменения на уровне файлов ожидаются.
- **DECISIONS** — что автор утвердил или запретил.
- **PLAYBOOK** — как работает Kimi Code и какой именно промпт отправить.
- **STATUS** — что реально сделано, что осталось, фактические хеши коммитов и очередь PENDING-AUTHOR.
- **CHANGELOG** — только история изменений документации.
- **echo-audit** — только архив доказательств, не источник инструкций.

## 4. Какую модель выбирать в Kimi Code

### 4.1. Одобренные варианты (из PLAYBOOK §7.1)

1. **K3.1 Pro (`k3.1-pro`)** с включённым Thinking и усилием **MAX** — основной выбор.
2. **K3 (`k3`)** с Thinking MAX — запасной вариант, если K3.1 Pro недоступна.

Других моделей инструкция не предполагает. Если в селекторе моделей вы видите другие названия: (1) посмотрите на фактический список; (2) выберите ближайшую из двух одобренных; (3) не выдумывайте и не предполагайте недоступную модель; (4) если недоступны **обе** одобренные — остановитесь и спросите совета, не начинайте задачу наугад.

### 4.2. Практическая матрица выбора

**Сложные и рискованные задачи — всегда K3.1 Pro с Thinking MAX:**

- Многофайловые или архитектурно чувствительные изменения: **T6, T8, T16, T18**.
- Service Worker, офлайн, кеш и версии: **T3, T7, T22** (SW-часть).
- Ленивая загрузка, сохранение состояния, глубокие ссылки: **T8, T18**.
- Жесты, тайминги, арбитраж событий: **T12, T13, T14**.
- Архитектура анимации VOICE: **T11**.
- Доступность, фокус, модальность: **T16**.
- Защита скрипта публикации: **T15**.
- Canvas-рендеринг, физика волн, адаптивная производительность, интеграция: **W-2, W-3, W-4, W-5, W-6, W-7, W-8**.
- CSS-фундамент, от которого зависят другие задачи: **T2**.
- **Любая** задача, где упали проверки, возник конфликт зависимостей, репозиторий расходится со спецификацией или под вопросом сохранность данных.

**Узкие, хорошо ограниченные задачи — может хватить K3 MAX (когда доступна):**

- Простые изолированные правки с явной приёмкой: **T1** (удаление мёртвой ссылки на скрипт), **T4** (удаление вызовов вибрации), **T17** (линейная формула задержки), **T19** (страница-заглушка noscript), **T20** (лицензионные файлы), **W-1** (документ параметров), **W-9** (отчёт).

**Важно:** если «простая» задача вдруг оказалась сложной — переключайтесь на более сильную модель, а не давите дальше. Рекомендация модели — это управление нагрузкой, а не гарантия: приёмочные проверки и ваш разбор остаются обязательными в любом случае. При сомнениях для многофайловой или рискованной задачи выбирайте более сильную модель.

### 4.3. Правило сессии

Если для переключения на K3.1 Pro в текущем интерфейсе Kimi Code нужно начать **новую сессию** — начинайте новую сессию (PLAYBOOK §7.1). Не рассчитывайте, что смена модели внутри старой сессии сохранит её состояние. Возобновляйтесь по IMPLEMENTATION-STATUS.md и истории Git — они и есть память проекта, а не чат.

## 5. Как видеть, что изменилось

Не обязательно понимать каждую строку кода. Контроль держится на трёх уровнях.

### 5.1. До задачи

- Откройте `IMPLEMENTATION-STATUS.md`: какая задача последняя выполнена, что следующее.
- Проверьте в терминале ветку и состояние дерева (команды ниже): ветка должна быть `work/echo-step4-implementation`, дерево — чистым.
- Убедитесь, что предусловия задачи (поле 10 промпта) выполнены.

### 5.2. Во время задачи

- Смотрите представление **Changes** в Kimi Code: список изменённых файлов.
- Сравните его с полями FILES/AREAS и DO-NOT-TOUCH в промпте задачи.
- Остановите работу, если появились посторонние, замороженные или необъяснимые файлы (единственное легальное дополнение к файлам задачи — `IMPLEMENTATION-STATUS.md`, плюс условное исключение S1 у W-5).
- Не одобряйте публикацию, операции с удалённым сервером, разрушительные команды Git.

### 5.3. После задачи

- Прочитайте отчёт о завершении целиком.
- Сверьте точный SHA коммита (длинный хеш вида `e2acadb…`).
- Посмотрите список изменённых файлов и **полный** diff (в Changes или командой `git show`).
- Различайте в результатах проверок: PASS (прошло), ранее записанный базовый сбой (был ещё в B-0), новый сбой (появился сейчас — стоп-условие) и PENDING-AUTHOR (ждёт вас).
- Убедитесь, что `IMPLEMENTATION-STATUS.md` обновился **в том же коммите**.
- Убедитесь, что дерево снова чистое.
- Только после этого — следующая задача.

### 5.4. Полезные команды (только чтение, ничего не ломают)

```powershell
git status --short --branch
git branch --show-current
git rev-parse HEAD
git log --oneline -10
git show --stat --oneline HEAD
git show --name-only --format="" HEAD
git diff --check
```

| Команда | Что она вам говорит |
|---|---|
| `git status --short --branch` | Текущая ветка и список незакоммиченных изменений. Пустой список = дерево чистое |
| `git branch --show-current` | Имя текущей ветки (ожидается `work/echo-step4-implementation`) |
| `git rev-parse HEAD` | Точный SHA последнего коммита — «на каком коммите мы стоим» |
| `git log --oneline -10` | Последние 10 коммитов одной строкой каждый — кто что сделал |
| `git show --stat --oneline HEAD` | Компактная сводка последнего коммита: сколько файлов и строк изменено |
| `git show --name-only --format="" HEAD` | Просто список файлов последнего коммита — сверяйте с охватом задачи |
| `git diff --check` | Поиск технических дефектов в незакоммиченных правках (пробелы, конфликтные маркеры) |

### 5.5. Почему хеш в журнале «отстаёт» на одну задачу — это нормально

Коммит не может содержать собственный хеш — он становится известен только после создания коммита. Поэтому устроено так: в коммите задачи её строка в `IMPLEMENTATION-STATUS.md` говорит `COMPLETE IN THIS COMMIT` с пометкой `pending post-commit resolution`, а **следующая** задача вписывает точный SHA предыдущей, читая фактическую историю Git. Предшественник определяется по реальной хронологии коммитов, а не по бумажному порядку задач — потому что Трек 2 может чередоваться с Треком 1. Реальный хеш текущего коммита всегда есть в отчёте Kimi о завершении. **Никогда не «исправляйте» коммит ради вписывания его собственного хеша** (никакого amend) — история не переписывается.

## 8. Как добавить новую главу между задачами внедрения

Это отдельная, самостоятельная инструкция. Книга продолжает писаться, пока Kimi Code выполняет инженерные задачи, — и это нормально. Добавление главы **не отменяет и не приостанавливает** работу по плану, но требует аккуратности, потому что `chapters.js` — единственный файл, который трогаете и вы, и (косвенно) план внедрения.

### 8.1. Какие файлы связаны с добавлением главы

По каждому файлу — четыре вопроса: что это, нужно ли его трогать, кто меняет, что сломается при ошибке.

**`chapters.js` — тексты глав.**

- *Что это:* объект `const chapterTexts = { ... }`. Ключи — целые числа **с нуля** (0–82, то есть 83 главы). Текст каждой главы — в **обратных кавычках** (шаблонная строка), внутри допустим HTML (`<p>…</p>`). В конце файла — `const PUBLISHED_AT = { ... }` с датами публикации отдельных глав.
- *Нужно ли трогать:* **да, всегда** — сюда добавляется текст новой главы.
- *Кто меняет:* **только вы. Никогда — Kimi Code.**
- *Что сломается при ошибке:* незакрытая обратная кавычка или случайный символ `` ` `` / `${` внутри текста ломает синтаксис всего файла — и сайт не загрузится вообще. Пропущенная запятая между ключами — то же самое.

**`index.html` — оглавление.**

- *Что это:* список пунктов вида `<a class="contents-item" data-chapter="N" href="?ch=N">NN <span class="dot"></span> Название</a>`, где `N` — индекс с нуля, а `NN` — видимый номер (индекс + 1, два знака). **Именно оглавление — хозяин порядка и названий глав**: номер главы, её заголовок и сам факт существования главы скрипт берёт из этого списка по позиции, а текст подставляет из `chapterTexts[N]`.
- *Нужно ли трогать:* **только если добавляете новый слот** (см. 8.2). Если заполняете уже существующий свободный пункт оглавления — не нужно.
- *Кто меняет:* только вы.
- *Что сломается при ошибке:* неверный `data-chapter` или `href` — глава не откроется или откроется не та; рассинхрон количества пунктов оглавления и ключей `chapters.js` — статическая проверка (до задачи T8) упадёт.

**`script.js` — логика сайта.**

- *Что это:* весь движок: построение списка глав из оглавления, разбор маркеров, навигация, прогресс.
- *Нужно ли трогать:* **нет, никогда.** Скрипт уже умеет подхватывать новые главы автоматически — по позиции в оглавлении.
- *Кто меняет:* только Kimi Code в рамках своих задач (T-серия).
- *Что сломается при ошибке:* если бы вы его тронули — перестали бы совпадать диагнозы и промпты задач, которые рассчитаны на конкретное состояние этого файла. Не трогайте.

**`style.css` — оформление.**

- *Что это:* все стили, включая классы `.voice-glitch`, `.photo-link`, `.placeholder`, `.contents-item`.
- *Нужно ли трогать:* **нет.** Все стили для глав и маркеров уже существуют.
- *Кто меняет:* только Kimi Code (T2, T9, T14, T22 и др.).
- *Что сломается при ошибке:* задачи T2/T9/T14/T22 правят конкретные места этого файла; ваши ручные правки создадут конфликты с их промптами.

**`sw.js` — Service Worker.**

- *Что это:* офлайн-кеш. В списке кешируемых файлов есть `chapters.js`; в начале файла — `CACHE_VERSION = 'echo-vNN'`.
- *Нужно ли трогать:* **да, одну строку** — поднять `CACHE_VERSION` на следующий номер (`echo-v66` → `echo-v67`), иначе публикация не пройдёт проверку, а читатели со старым кешем не увидят главу.
- *Кто меняет:* только вы (одна строка перед публикацией).
- *Что сломается при ошибке:* забудете — `push-echo.cmd` сам остановится и напомнит; если как-то опубликуете без подъёма версии — читатели получат старый `chapters.js` из кеша.

**`version.js` — видимая версия.**

- *Что это:* строка `ECHO_VERSION`, отображаемая на сайте.
- *Нужно ли трогать:* по вашей установившейся практике (автоматическая проверка на него сейчас не настроена; механику версий после задачи T3 определяет план).
- *Кто меняет:* только вы.
- *Что сломается при ошибке:* ничего технически; это отображаемая строка.

**`tests/` — проверки и служебные скрипты.**

- *Что это:* `run-static.ps1` (статические проверки перед публикацией), `build-meta.ps1` (генератор `chapters-meta.js` — структурного зеркала `chapters.js`), `serve.ps1` (локальный сервер).
- *Нужно ли трогать:* не редактировать, но **запускать** (см. 8.5).
- *Кто меняет:* содержимое — только Kimi Code (T2, T6, T8); запускаете вы.
- *Что сломается при ошибке:* если не пересобрать `chapters-meta.js` **до выполнения задачи T8** — статическая проверка упадёт и не даст опубликовать (подробности в 8.4).

**`images/` — фотографии.**

- *Что это:* `img_01.jpg`–`img_05.jpg` используются маркерами `{{PHOTO:…}}`; `img_06.jpg` — **зарезервирован**, не подключён.
- *Нужно ли трогать:* нет. Фото-подсистема заморожена.
- *Кто меняет:* никто.
- *Что сломается при ошибке:* ссылка на несуществующий файл даст «битое» фото-слово в тексте.

### 8.2. Процедура добавления главы (14 шагов)

**Сначала решите, куда добавляете.** В проекте уже есть свободный слот: последний пункт оглавления — `data-chapter="83"`, глава 84 «Следующая наша встреча», для которой в `chapters.js` **нет** ключа 83. Такие главы-заглушки отмечены в оглавлении классом «в работе» и пропускаются всеми переходами. Поэтому есть два пути:

- **Путь А (проще): заполнить свободный слот** — добавить в `chapters.js` ключ 83. Оглавление менять не нужно вовсе.
- **Путь Б: добавить новый слот в конец** — добавить и пункт оглавления (индекс 84, номер 85), и ключ 84.
- **Вставку в середину не планируйте без крайней нужды:** номера глав жёстко привязаны к позиции — придётся перенумеровать все последующие пункты оглавления и сдвинуть все ключи `chapters.js` после места вставки. Это долго и рискованно.

Дальше — шаги (для пути Б добавьте шаг 3а):

1. Убедитесь, что рабочее дерево чистое: `git status --short --branch` — пусто, ветка `work/echo-step4-implementation`. Добавление главы не должно смешиваться с незаконченной задачей Kimi.
2. Откройте `chapters.js`, найдите конец объекта `chapterTexts` — последний существующий ключ (сейчас 82) и закрывающую скобку `};`.
3. Добавьте новый ключ **следующим номером**, текст — в обратных кавычках, абзацы — в `<p>`. Нейтральный пример формы (не образец текста):

   ```js
       83: `<p>ПЕРВЫЙ АБЗАЦ ТЕКСТА</p>
   <p>ВТОРОЙ АБЗАЦ С {{VOICE:standard}}ФРАЗОЙ ГОЛОСА{{/VOICE}} ВНУТРИ СТРОКИ</p>`
   ```

   Ключи разделяются запятыми; после последнего ключа запятая не обязательна.
3а. *(Только путь Б.)* В `index.html` добавьте в конец списка оглавления пункт со следующим индексом и номером:

   ```html
   <a class="contents-item" data-chapter="84" href="?ch=84">85 <span class="dot"></span> НАЗВАНИЕ ГЛАВЫ</a>
   ```

4. Проверьте текст на запрещённые символы: внутри обратных кавычек **нельзя** использовать сам символ `` ` `` и комбинацию `${` — они сломают файл. Кавычки-ёлочки и обычные кавычки — можно.
5. Проверьте маркеры по правилам раздела 8.3: пары, режимы, фото-слова.
6. Убедитесь, что ключи идут подряд без дырок и дублей: `grep -oE '^\s+[0-9]+:' chapters.js` (или поиск `    83:` в редакторе).
7. **Если задача T8 ещё не выполнена** — пересоберите зеркало метаданных: `pwsh tests/build-meta.ps1`. Файл `chapters-meta.js` обновится автоматически. Если T8 выполнена — пропустите шаг (см. 8.4).
8. Поднимите `CACHE_VERSION` в начале `sw.js`: `echo-vNN` → следующий номер. Одна строка.
9. Прогоните статические проверки: `pwsh tests/run-static.ps1`. Все строки должны быть PASS.
10. Поднимите локальный сервер: `pwsh tests/serve.ps1 -Port 8734` и откройте сайт в браузере.
11. Ручная проверка: глава видна в оглавлении с правильным номером и названием; открывается; голосовые вставки подсвечены; фото-слова открывают фотографии; переходы «предыдущая/следующая» работают; старые главы не пострадали.
12. Остановите сервер. Закоммитьте **отдельным авторским коммитом** — только `chapters.js` (+ `index.html`, `chapters-meta.js`, `sw.js`, если менялись): например, `git add chapters.js sw.js && git commit -m "Добавлена глава 84"`.
13. Опубликуйте как обычно — через `push-echo.cmd` (это делаете только вы; Kimi Code не публикует никогда).
14. Запишите факт добавления в журнал сеанса (или упомяните в следующем промпте возобновления Kimi): какая глава, какой ключ, дата. Это нужно, чтобы следующая задача Kimi учитывала новое состояние файла. Статусы задач T/W в `IMPLEMENTATION-STATUS.md` из-за добавления главы **не меняются**.

### 8.3. Маркеры в тексте глав — проверенные факты

Факты ниже установлены по коду парсера (`script.js`, строки ≈740–752) и по зафиксированному снимку репозитория. Где что-то установить нельзя — так и написано.

**Голосовые маркеры.** Форма: `{{VOICE}}…{{/VOICE}}` или `{{VOICE:режим}}…{{/VOICE}}`. Текущее состояние текста книги: открывающих `{{VOICE}}` без режима — **6**, `{{VOICE:standard}}` — **37**, закрывающих `{{/VOICE}}` — **43**: пары сбалансированы (6 + 37 = 43). Маркеров `:strong` и `:whisper` в тексте сейчас **ноль** — эти режимы предусмотрены решением D-3 и будут поддержаны архитектурно в задаче T11; вы можете начать использовать их в новых главах только после того, как T11 выполнена и вы убедились в отрисовке. Режим без указания (`{{VOICE}}`) сейчас отображается как `aggressive` — это поведение по умолчанию в текущем коде; T11 приводит его к решению D-3.

**Жёсткие ограничения парсера (проверено по регулярным выражениям в коде):**

- **Вложенность НЕ поддерживается.** Разбор — одиночным регулярным выражением, без рекурсии: `{{VOICE}}…{{VOICE}}…{{/VOICE}}…{{/VOICE}}` сломается — внутренний закрывающий маркер «закроет» внешнюю вставку досрочно. Никогда не вкладывайте голосовые маркеры друг в друга.
- **Пара должна жить внутри одной строки/абзаца.** Регулярное выражение без флага многострочности: `.*?` не пересекает перевод строки. Держите `{{VOICE…}}` и его `{{/VOICE}}` в пределах одного `<p>…</p>` без ручных переносов строки внутри.
- Имя режима — только латинские буквы, цифры и подчёркивание (`\w+`), без дефисов и пробелов.
- Нераспознанный режим не ломает страницу, но и не даёт ожидаемого оформления — используйте только существующие режимы.

**Фото-маркеры.** Форма строго одна: `{{PHOTO:слово:файл.jpg}}` — одиночный строчный маркер (без пары). В книге сейчас 5 таких маркеров, файлы `img_01.jpg`–`img_05.jpg`. **`img_06.jpg` зарезервирован** — не подключайте его без отдельного решения. Фото-подсистема заморожена: Kimi её не трогает, новых форм маркера не существует.

**`PUBLISHED_AT`.** Список дат публикации отдельных глав (сейчас ключи 69–72). **Не редактируйте и не удаляйте** — механизм бейджа «новая глава» упраздняется задачей T6, но сама запись — ваши данные, и T6 её сохраняет.

**Чего установить не удалось** — и это честный ответ: явных письменных правил «сколько голосовых вставок допустимо на абзац» или «какие сочетания режимов в одной главе уместны» в коде и документах нет. Это вопрос вашего авторского вкуса, а не технический лимит. Не выдумывайте для себя ограничений, которых нет, — но и не полагайтесь на поведение, не проверенное в браузере.

### 8.4. `chapters-meta.js` и задача T8

`chapters-meta.js` — автоматически генерируемое структурное зеркало `chapters.js` (сам сайт его не загружает; он нужен проверкам). Правило зависит от того, выполнена ли задача T8:

После **любого** изменения `chapters.js` запускайте `pwsh tests/build-meta.ps1` и коммитьте обновлённый `chapters-meta.js` вместе с главой. Иначе `run-static.ps1` упадёт, а `push-echo.cmd` не даст опубликовать.

### 8.5. Последовательность проверки после добавления

По порядку, ничего не пропуская:

1. `node --check chapters.js` не требуется — синтаксис проверит статический прогон, но если сомневаетесь: `pwsh tests/run-static.ps1` покажет синтаксическую ошибку первой.

3. Локальный сервер + браузер: новая глава в оглавлении, открывается, маркеры работают, соседние главы и переходы не пострадали.
4. Консоль браузера (F12) — без красных ошибок на новой главе.
5. Только после этого — коммит и публикация.

### 8.6. Как это сочетается с работой Kimi Code (между задачами)

- Добавление главы — **ваш отдельный коммит**, никогда не часть коммита задачи Kimi и не параллельно с ним: сначала доведите текущую задачу до чистого дерева, потом добавляйте главу (или наоборот), но не смешивайте.
- **Базовый уровень B-0 не переписывается.** Если вы добавили главу после прогона B-0, это намеренное авторское изменение, а не «новый сбой базы»: в журнале сеанса отметьте, что изменение ваше, чтобы следующая задача не приняла его за регрессию.
- Статусы задач T/W в `IMPLEMENTATION-STATUS.md` из-за добавления глав **не меняются** — файл статуса правит только Kimi внутри своих коммитов.
- Если очередная задача Kimi работает с `chapters.js` по соседству (например, T6 удаляет мёртвый код бейджей, T8 упраздняет проверку метаданных), она обязана сохранить ваши тексты нетронутыми; проверьте в diff её коммита, что изменения не коснулись текста глав.
- **Kimi Code никогда не редактирует содержание глав от вашего имени.** Если в отчёте задачи вы видите правки текста глав — это стоп-условие: разбирайтесь, не принимайте.

### 8.7. Запреты (добавление глав)

- Не давайте Kimi Code добавлять, переписывать или «улучшать» тексты глав — ни целиком, ни по одному слову.
- Не вставляйте реальные фрагменты текста книги в промпты, отчёты, документацию или эту инструкцию — везде только нейтральные заглушки.
- Не меняйте порядок глав и не перенумеровывайте опубликованные главы без крайней нужды — номера зашиты в ссылках читателей (`?ch=N`, `#ch-NN`).
- Не трогайте `PUBLISHED_AT`, фото-подсистему, `img_06.jpg`, `script.js`, `style.css`.
- Не выдумывайте новые виды маркеров и не используйте `:strong`/`:whisper` до выполнения T11.
- Не вкладывайте голосовые маркеры друг в друга и не разрывайте пару переводом строки.
- Не публикуйте, пока не прошли проверки из 8.5.

### 8.8. Два потока работ

| | Поток А: текст книги | Поток Б: инженерия |
|---|---|---|
| Что | Главы, названия, маркеры, порядок | Код, стили, SW, тесты, вода, документы |
| Кто | Только вы | Kimi Code по промптам PLAYBOOK |
| Коммиты | Ваши авторские, отдельные | Одна задача = один коммит |
| Файл пересечения | `chapters.js` — ваш | `chapters.js` — для Kimi только узкие механические операции по задачам, без текста |
| Контроль | Ваши проверки 8.5 | Приёмка задач + IMPLEMENTATION-STATUS.md |

**Центральный принцип:** текст книги — ваша территория, код — территория Kimi Code. `chapters.js` лежит на границе, и на границе действует самое строгое правило проекта: **Kimi Code никогда не редактирует содержание глав.**
